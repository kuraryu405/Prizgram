# 就活パーソナルエージェント 企画書

**プロダクト名: prizgram**

## 1. 背景

現在の日本の新卒・インターン就活市場には、情報アクセスの格差が構造的に存在する。

- 都市部大学、体育会系ネットワーク、強い OB/OG 組織を持つ学生は、選考対策・企業研究・ES 添削といった非公開ノウハウに容易にアクセスできる
- 地方大学生、初めて就活に臨む学生、キャリアセンターや先輩とのつながりが薄い学生は、同水準の情報を得る手段が限られている
- 既存の就活支援サービス（逆求人型媒体、スカウト型サービス等）の多くは「検索・マッチング」機能にとどまり、選考結果を踏まえて自己理解を継続的に更新する仕組みを持たない

## 2. 目的

就活における情報・機会格差を、継続的に学習・更新する「パーソナルエージェント」によって縮小する。単発の検索ツールではなく、ユーザーの選考結果や面接内容を踏まえて自律的に自己理解（ペルソナ）を更新し、そのたびにマッチング精度を高めていく仕組みを提供する。

## 3. ターゲットユーザー

社会的貢献の観点を重視し、以下の層を主要ターゲットに据える（個人の就活効率化としての価値もあるが、これは副次的な位置づけとする）。

- 地方大学・情報系以外の学部に所属し、体系的な就活対策を受けにくい学生
- 初めて就活・インターン選考に臨み、自己 PR の言語化に不慣れな学生
- キャリアセンターや強い OB/OG ネットワークへのアクセスが弱い学生

## 4. サービス概要

対話を通じて仮の「就活ペルソナ」（強み・弱み・志向性・スキル）を生成し、それを軸にインターン・求人をスコアリングして提示する。選考結果や面接内容をフィードバックとして取り込み、ペルソナを継続的に更新することで、時間とともにマッチング精度と自己理解の解像度を高めていく。

## 5. 主要機能

### 5.1 ペルソナ生成

対話形式のヒアリングを通じて、経験・スキル・価値観を構造化データとして抽出し、仮の就活ペルソナを生成する。

### 5.2 求人・インターンのスコアリングと提示

ペルソナと求人票を突き合わせ、単一の総合スコアではなく、軸ごとのスコアと根拠を提示する（ブラックボックス化の回避）。

- スキル要件充足度（経験・資格の客観的な一致率）
- 企業文化・価値観フィット（ペルソナの志向性との一致）
- 選考難易度と現在の実力のギャップ（面接フィードバック履歴から算出）

### 5.3 選考状況・締切の管理とリマインド

応募中の企業・選考ステータス・締切（ES 提出、面接日程、内定承諾期限など）を一元管理する。締切が近づくと自律的に検知し、優先度付きでリマインド通知を生成する。複数社の締切が重なる場合は、緊急度の高いものから提示する。

### 5.4 面接フィードバック

模擬面接の文字起こしを LLM が分析し、改善点・強み・話し方の癖をフィードバックする。内容は自動的にペルソナへ反映され、以降のスコアリングや ES 対策に活かされる。

> 本番の企業面接そのものの録音・分析は対象外（6.3 参照）。

### 5.5 応募書類の下書き生成

ペルソナと求人要件をもとに ES・志望動機の下書きを生成する。最終的な文言確定と提出判断は必ずユーザー自身が行う（6.1 参照）。

## 6. 倫理設計・自律範囲の境界線

エージェントに何を任せ、何を任せないかを明確に線引きする。

| フェーズ               | エージェントの自律範囲     | 理由                                         |
| ---------------------- | -------------------------- | -------------------------------------------- |
| 求人収集・スコアリング | 自律で実行                 | 情報整理であり、対外的な意思表示を伴わない   |
| 面接フィードバック     | 自律で実行                 | 自己分析支援であり、対外的行為ではない       |
| ES 下書き生成          | 自律で下書きまで           | 最終文言は本人選択が前提であれば代筆性は薄い |
| **応募の送信**         | **人間の承認を必須とする** | 対外的な意思表示・契約行為の入口であるため   |

### 6.1 自動応募を実装しない理由

- 求人媒体・採用サイトの多くは ToS で自動応募・自動投稿を禁止しており、規約違反リスクが高い
- 自動応募が可能になると本気度の低い応募が増加し、企業側の選考コスト増加 → フィルタ強化 → 応募者全体の選考難化、という負の外部性を招きうる
- AI が生成した志望動機をそのまま「本人の言葉」として提出することは代筆性を帯びる

### 6.2 スコアリングの説明可能性

「マッチ度 ◯%」のような単一指標のみの提示はブラックボックス化を招くため行わない。軸ごとの内訳と根拠の開示を必須仕様とする。

### 6.3 面接録音の扱い

録音・分析の対象は模擬面接（友人・キャリアセンター等との練習）に限定する。企業本番面接の無断録音は規約上・心証上のリスクがあるため機能対象外とする。

## 7. エージェントとしての技術的位置づけ（RAG との差別化）

単純な検索・提示（RAG 的な設計）との違いは、以下 4 条件を満たす点にある。

| 条件             | 本企画での実装                                                                                                     |
| ---------------- | ------------------------------------------------------------------------------------------------------------------ |
| 自律性           | 新着求人・選考結果・締切接近といったイベントをトリガーに、自動でペルソナ更新・再スコアリング・リマインド生成を実行 |
| 複数ステップ計画 | ヒアリング → 構造化 → マッチング → フィードバック反映 → 再マッチングの多段パイプライン                             |
| ツール利用       | 求人 DB 検索、文字起こし解析、ES 下書き生成など複数ツールを状況に応じて呼び出す                                    |
| 状態・記憶       | ペルソナと選考履歴を DB に永続化し、時間経過とともに判断精度を更新する                                             |

## 8. 技術構成（確定）

- フロントエンド: Next.js / React / TypeScript
- バックエンド: Next.js API Routes（Route Handlers）を想定（独立したバックエンドフレームワークは未指定）
- DB: SQLite
- LLM: OpenAI 互換 API
- デプロイ先: AWS EC2
- 非同期処理: 締切監視・リマインド生成は、EC2 上での cron（node-cron 等）によるバッチ処理を想定

## 9. 社会的貢献の整理

| 観点                 | 内容                                                                                                                           |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 対象となる社会課題   | 就活における情報・ノウハウ格差（都市部・強ネットワーク層 vs 地方・情報弱者層）                                                 |
| 介入方法             | 対話による自己理解支援と継続的なペルソナ更新により、体系的な指導を受けられない学生の自己 PR 言語化とマッチング精度を底上げする |
| 既存サービスとの違い | 検索型サービスは「探す」段階で終わるが、本企画は選考結果を踏まえて自己理解そのものを更新し続ける点が異なる                     |
| 留意点               | 「作ったから貢献している」で終わらせず、利用前後の ES 通過率の変化など効果測定の仕組みを今後設計する必要がある                 |

## 10. リスクと対応

| リスク                                    | 対応方針                                                                      |
| ----------------------------------------- | ----------------------------------------------------------------------------- |
| 求人媒体の ToS 違反（自動取得・自動応募） | 求人データは公式 API または許諾ベースの取得に限定し、自動応募機能は実装しない |
| スコアリングのブラックボックス化          | 軸別内訳の開示を必須仕様とする                                                |
| ES 下書きの代筆性                         | 下書きという位置づけを明示し、最終提出は必ずユーザーの手動操作を挟む          |
| 模擬面接以外の録音利用                    | 本番面接の録音・分析機能は実装しない                                          |

## 11. MVP スコープ（初期実装範囲）

1. 対話型ヒアリングによるペルソナ生成
2. 求人票との軸別スコアリング表示
3. 選考状況・締切の一元管理とリマインド通知

面接フィードバックと ES 下書き生成は、MVP 検証後のフェーズ 2 として位置づける。
